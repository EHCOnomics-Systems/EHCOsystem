# Ecosystem Claim → Evidence Matrix

This matrix maps selected public Instantiated AI / EHCOsystem propositions to the evidence class that supports them. It distinguishes the **public reference** a reviewer can inspect from the **verification method** used to source-ground a claim. A public architecture page is not treated as implementation evidence merely because it summarizes an implementation-grounded proposition.

The matrix also keeps **estate lane**, **current development / maturity posture**, **evidence class**, **currentness**, and **proof ceiling** separate. Components in the same estate lane do not automatically have the same maturity. No universal percentage or completion denominator is asserted.

Where controlled source review is required but the underlying source is not publicly transferred, that fact is stated explicitly. Private repository names, private revisions, Drive IDs, protected internal paths, and confidential control locators are not published here.

## Verification discipline

For a deeper review, identify the exact proposition first, then inspect the evidence class that can establish it. The **public source / approved public reference** column identifies what is openly inspectable. The **verification method** and **source-review date** columns identify how the proposition was source-grounded. They are intentionally separate so a public summary document is not mistaken for the implementation or effect evidence it summarizes.

A category definition, repository commit, test fixture, container image, deployment record, or Runtime receipt should not be substituted for another evidence class simply because it is convenient. Estate-lane placement does not create maturity, authority, Runtime participation, or evidence. For the detailed Runtime/repository/test-estate interpretation, use the [canonical boundary record](../architecture/runtime-repository-and-test-estate-boundary.md).
