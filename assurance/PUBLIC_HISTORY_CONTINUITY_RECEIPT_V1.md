# EHCOsystem Public History Continuity Receipt v1

## Purpose

This receipt records the continuity requirements for the SOW-010 public Git-history privacy remediation. The remediation changes historical Git ancestry and provider custody only where required to remove protected implementation/source-topology exposure. It does not demote, weaken, reclassify, or re-prove accepted public-safe technical evidence.

## Accepted pre-remediation source state

- Accepted public repository: `EHCOnomics-Systems/EHCOsystem`
- Accepted pre-remediation main: `a5e1fb7ec73e12534fce47b15bce86927549065e`
- Accepted pre-remediation tree: `7999a0747585f096f9d1e53236ce4c55f8add1c0`
- Accepted numerical standing: `52/53`

The accepted tree identity is the preservation anchor for public file content. History remediation may change commit identities because commit identity includes ancestry. That commit-identity change is not a change to the technical evidence represented by unchanged file/blob content.

## Preservation invariant

The history-remediation operation SHALL NOT reduce or demote accepted public-safe technical content merely to make history cleanup easier. Unless a separately established public-safety defect requires an exact correction, the remediation preserves:

- accepted architecture and system descriptions;
- accepted technical claims and claim ceilings;
- accepted Runtime public representation and authority boundaries;
- accepted Language Model capability and verification records;
- accepted Range Reactor benchmark and semantic-closure results;
- accepted Full Flex public evidence records;
- accepted quantitative results and evidence classes;
- public verification code, public-safe fixtures and validation depth;
- public dossiers, diagrams, navigation and reader-facing technical language;
- accepted maturity statements; and
- accepted numerical standing `52/53`.

No technical claim becomes weaker merely because historical Git ancestry is replaced.

## Removal target

The remediation target is limited to protected public-history/provider exposure classes, including protected implementation/source custody locators, protected source revisions or branches, internal Drive/control routing locators, protected evidence-custody locators, protected host/infrastructure topology and equivalent private routing information that remains reachable only through historical Git/provider surfaces.

Public-safe evidence depth is not a removal target.

## Continuity model

The intended transition is:

`ACCEPTED_PRE_REMEDIATION_MAIN`
→ `ACCEPTED_PRE_REMEDIATION_TREE`
→ `DISCLOSURE_SAFE_HISTORY`
→ `POST_REMEDIATION_ACCEPTED_MAIN`

The post-remediation accepted state must preserve the accepted technical content represented by the preservation anchor, subject only to explicitly declared public-safety/control records required to perform and document the remediation.

## Git identity consequence

A destructive history rewrite necessarily changes commit SHAs in the rewritten suffix and may invalidate old commit signatures, commit URLs and PR-to-commit lineage. Those consequences concern Git history identity and provider lineage; they do not by themselves alter the evidence class, measured result, capability, maturity, Runtime state, authority, participation or standing represented by preserved public content.

Old public commit identifiers may be retained only as public-safe pre-remediation lineage references where doing so does not preserve or re-expose protected topology. Protected private identifiers are not reproduced in this receipt.

## Provider boundary

At preparation time, canonical `main` is subject to active non-fast-forward protection. The preparation stage does not weaken that rule, force-update `main`, replace the repository, or claim provider purge completion. Cutover and any provider-side dereferencing/purge remain dependent on an explicit lawful provider route and owning-provider postcondition readback.

## Non-effects

This receipt creates no Runtime, deployment, production, release, authority, participation or standing effect. It does not make EHCO1 a Runtime authority and does not originate technical standing. `INSTANTIATED_EHCO_RUNTIME` retains Tier One Runtime authority/current Runtime state.
