## 30-minute review

### 1. Category qualification

Review the Instantiated AI definition first. The architectural question is whether governing computational conditions such as identity, authority, state, source, memory, permissible range, evidence, release, and consequence are established independently of the intelligence before consequential operation.

The category definition is architecture, not self-certification. Its qualification questions identify what a candidate system must be able to establish without treating model assertion as final authority.

### 2. EHCOsystem architecture

Review EHCOsystem as EHCOnomics' **Instantiated AI ecosystem**. EHCO AI-OS is the **realized Tier One Runtime** foundation; downstream governed components own separate computational, evidence, research, relationship, coordination, and application functions; Tier Three provides interfaces and projections.

Runtime participation is not inferred from ecosystem membership. Persistent component identity, build, deployment, application execution, registration, or public representation remain separate from scoped Runtime participation.

### 3. Computational ownership

Inspect the component sections for:

- **EHCO Language Model** — deterministic computational language;
- **EHCO Range Reactor** — bounded range/reasoning computation;
- **EHCO RAG** — retrieval/evidence/context;
- **EHCO Memory** — memory/continuity research foundation;
- **Primordia, Recursion, and Fractal Systems** — governed research foundations;
- **EHCO Prime** — persistent individual-facing relationship service;
- **EHCO Agent Connect** — registry/discovery/compatibility/candidate-routing coordination.

The diligence question is not whether every component has identical maturity. It is whether ownership, maturity, evidence class, and proof ceiling are explicit.

### 4. Domain applications

Representative application estates include Grasp Safety, EHCO Energy, Noble Law, EHCO War Room, HTPI, EHCO Project Construct, EHCO Luminis, EHCO Nexus, EHCO Permit Trace, and Pegasus IT. Evaluate application-local realization independently from any scoped Runtime participation proposition.

### 5. Inspectable evidence

The current Language Model snapshot is the first direct public component-test example. Other component evidence packages should be published only through separately reviewed disclosure and verification operations.

## Deep review method

For each proposition:

1. identify whether it is a category, ecosystem, component, application, evidence, or Runtime proposition;
2. identify the governed object and computational owner;
3. identify the evidence class required by the proposition;
4. inspect the public artifact, test fixture, source anchor, observation, or receipt that supports that evidence class;
5. verify exact identity, provenance, and time/currentness where material;
6. inspect claim-specific discrepancies or limitations;
7. where unrestricted public evidence is intentionally bounded, define the minimum controlled diligence necessary to establish the remaining proposition without transferring the complete proprietary implementation.

## Component qualification versus complete-system benchmark

Component qualification and complete-system benchmarking are different evidence classes. Individual component tests establish bounded component behavior. A complete comparative benchmark should be reserved for an integrated system and should declare its method and measure end-to-end qualities such as latency, throughput, compute, model/API calls, token use, replayability, withholding/failure behavior, evidence, human review, output quality, and cost.
