## Public-record corrections
Use the repository's [public documentation/evidence issue template](../.github/ISSUE_TEMPLATE/public-documentation.yml) for bounded questions about architecture, evidence, navigation, provenance, or verification records.

## Technical proof challenges
Use the [technical challenge issue template](../.github/ISSUE_TEMPLATE/technical-challenge.yml) for reproducibility problems, proof-protocol questions, evidence-routing concerns, or public-verification issues that can safely be discussed in public.

## Security or sensitive disclosure
Do not publish vulnerabilities, credentials, private implementation details, protected repository or source topology, privileged endpoints, or protected infrastructure information in a public issue.

Read [SECURITY.md](../SECURITY.md) before reporting a sensitive concern. It directs vulnerability reports, suspected credential exposure, implementation-sensitive findings, and operational-security concerns to an official private EHCOnomics contact channel rather than a public issue.

The public repository does not currently publish a specific private security address. Do not infer or invent one from public material.

## FAQ / challenge discipline

**Does a public issue change Runtime state or standing?** No. A correction, challenge, issue, comment, or reviewer observation does not by itself change Runtime state, Runtime authority, standing, deployment, or component lifecycle state.

**Does a passing repository validator prove the whole Runtime?** No. Repository validation establishes the public repository representation and intentionally public proof objects. Runtime and component propositions remain owned by their applicable evidence domains.

**Can public review require proprietary implementation source?** Not by default. SOW-10 publishes public-safe evidence and verification while preserving proprietary implementation custody. Any deeper controlled access is a separate case-specific decision.

**Where should reproducibility concerns go?** Use the technical challenge route when the issue can be discussed safely in public; use the private security route when disclosure could expose protected information.
