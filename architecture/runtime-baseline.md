# Immutable Runtime Baseline

AI governance cannot begin after intelligence has already shaped an operation. Once a model has interpreted a request, framed evidence, generated a response, recommended an action, or influenced a decision, the system is no longer establishing the conditions under which intelligence may participate. It is reviewing something that has already taken form.

Governance must therefore be instantiated upstream.

The underlying authority does not originate in the Runtime. It originates with a valid person, organization, institution, office, credential issuer, contract, law, system of record, or other recognized source with standing over the relevant domain. Runtime Authority operationalizes that authority by determining what the governed system may recognize as valid, which participants may enter an operation, how their roles are bounded, what state may change, and what may be persisted, released, corrected, recovered, or carried into consequence.

## Constitutional order

> Authority source → identity → role → eligibility → admission → transaction binding → scope and purpose → participant invocation → candidate return → validation → authoritative disposition → recognized state transition → persistence or release → consequence → evidence → correction or recovery

This is not a conventional workflow. It defines which class of object may exist before another can become authoritative. An operation may stop, withhold, challenge, return, quarantine, recover, or re-enter only through governed transitions.

## Runtime Authority

Runtime Authority remains controlling over admission, transaction binding, recognized operational state, authoritative disposition, persistence, release, correction, recovery, and consequence.

A participant may exist before admission. It may possess capability before eligibility. It may produce a candidate before validation. It may return evidence before any authoritative disposition has occurred.

## Language-model position

The language model remains downstream. It cannot admit itself, determine its own standing, issue its own operative invocation, authorize its return, create recognized state, or promote generation into consequence.

## Baseline separations

- Capability is not authority.
- Permission is not standing.
- A proposal is not a disposition.
- Execution is not authorization.
- Evidence is not proof.
- Testing is not deployment.
- Deployment is not admission.
- Generation is not Runtime recognition.
- A ledger is evidence, not authority.
- A dashboard is projection, not Runtime truth.
- Observation and scope miss do not create state change.

A boundary proves only what occurred within its declared scope. It cannot support an end-to-end governance claim without proof that the governed condition survived beyond it.

Implementation, verification, integration, deployment, admission, Runtime participation, standing, production operation, and release remain separate proof states. None automatically promotes another.

## Status and proof ceiling

This document states the accepted public Runtime baseline. It does not publish the proprietary Runtime implementation or claim that every surrounding participant, integration, deployment, or production environment is governed merely because it connects to the Runtime.
